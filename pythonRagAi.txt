# Smart Doc Ai

You are an expert full-stack AI developer, Python developer, React developer, Flask developer, and RAG engineer.

Build a complete, production-style academic project called:

# Smart Doc Ai

## Project Goal

Build a full-stack web application where college students can:

* Register and log in securely.
* Upload one or multiple PDF documents.
* Categorize uploaded documents.
* Ask questions about uploaded documents.
* Receive AI-generated answers based only on relevant uploaded content.
* View the source document and page number for each answer.
* Maintain chat sessions and chat history.
* Search across multiple academic documents.
* Filter questions based on document categories.
* Analyze previous question papers.
* Identify repeated or frequently asked questions/topics.
* Suggest important topics for exam preparation.

The project must use a proper **React frontend**, **Python Flask backend**, **MySQL relational database**, **ChromaDB vector database**, **Sentence Transformers embeddings**, **PyMuPDF for PDF processing**, and **Ollama as the local LLM**.

Do not build a simple demo. Build a properly structured, modular, efficient, maintainable full-stack application.

# 9. PDF Processing Requirements

Use PyMuPDF.

Process PDFs page by page.

For every extracted text section, preserve:

* document_id
* user_id
* filename
* category_id
* page_number
* chunk_index

If a PDF contains no extractable text, return a useful error or mark it as unsupported.

Structure the PDF processor so OCR support can be added later.

# 10. Text Chunking Strategy

Implement efficient chunking.

Recommended initial configuration:

* Chunk size: approximately 800–1200 characters or a token-aware equivalent.
* Chunk overlap: approximately 100–200 characters.

The implementation should avoid breaking sentences unnecessarily.

Each chunk must maintain metadata.

Example metadata:

{
"document_id": 15,
"user_id": 4,
"category_id": 2,
"filename": "Python_Notes.pdf",
"page_number": 24,
"chunk_index": 3
}

Create a reusable chunking service so chunking parameters can be changed through configuration.

# 11. Embedding System

Use Sentence Transformers.

Create a dedicated embedding service.

Requirements:

* Load the embedding model once during application startup where practical.
* Avoid reloading the model for every request.
* Generate embeddings in batches.
* Handle long document processing efficiently.
* Use the same embedding model for document chunks and user queries.

The embedding service must expose methods such as:

* embed_documents()
* embed_query()

Keep the implementation independent enough that the embedding model can be replaced later.

# 12. ChromaDB Vector Database

Use persistent ChromaDB storage.

Each vector should contain:

* unique chunk ID

Metadata must include:

* document_id
* user_id
* category_id
* filename
* page_number
* chunk_index

Use metadata filtering so users can:

* Search only their own documents.
* Search a specific document.
* Search a specific category.

Example:

A user asks:

“What are the important Unit 3 topics?”

The retrieval system should search only documents belonging to that authenticated user.

Never allow one user to retrieve another user's document embeddings.

# 13. RAG Pipeline

Implement a dedicated RAG service.

The question-answering flow should be:

1. Authenticate user.
2. Receive question.
3. Receive optional filters:

   * document ID
   * category ID
   * chat session ID
4. Generate query embedding.
5. Search ChromaDB.
6. Retrieve the top relevant chunks.
7. Remove duplicate or highly similar chunks if necessary.
8. Prepare a clean context.
9. Send the context and question to Ollama.
10. Generate an answer.
11. Return the answer and sources.
12. Store the question and answer in MySQL.
13. Store source references in message_sources.

Use a configurable Top-K value.

For example:

TOP_K = 5

The LLM prompt must clearly instruct the model:

“You are an academic assistant. Answer the user's question using only the provided context. If the answer cannot be found in the context, clearly state that the information is not available in the uploaded documents. Do not invent information.”

Always encourage grounded answers.
